# Part 2｜TikTok LIVE 观众视角 × 表情 AR 互动：产品工作说明

版本：2026-10-22（补充互动入口假设）｜状态：本地网页 Demo 的执行基线。下文明确区分原始需求、已确认的体验约束、TikTok 已有交互事实与本原型的设计假设；候选规则和数值不是平台官方标准。

**2026-10-21 交付补充：**直播观看画面保留主播、观众、评论和底部互动入口；原先覆盖画面的 LIVE／本地演示／互动挑战、识别状态、倒计时与摄像头控制已移到框旁的“互动实验台”或删除。图像验证入口只在本地开发版与开机预览版显示，公开构建自动隐藏入口并剔除测试素材。捂嘴大笑必须有手遮嘴、双侧苹果肌上扬与双侧笑眼等当前证据；单纯遮嘴不放烟花。下文涉及旧版画面内调试元素的设计细节仅作为历史方案。

**2026-10-21 持续效果规则：**原始需求没有给雨或烟花的固定时长，当前采用“表情维持、特效维持”的交互假设。微笑确认后只播放一次云聚拢和闪电开场，随后雨持续；大笑确认后烟花按预制波次持续升空。短暂识别波动使用滞回；稳定回到平静才平滑收束，并在收束后冷却 2 秒。微笑与大笑直接转换时先收束旧效果、再识别并播放新效果，无须插入平静表情，也不会同时叠加。以下涉及固定 7／9 秒的旧版本测试记录只作历史证据。

## 0. 一页结论

**要做的体验：**网页第一眼就是一间竖屏 TikTok LIVE 风格的直播间。用户在这个**观众视角**中看见“主播”的实时视频；Demo 暂以本机摄像头扮演主播，方便同一人独立测试。默认自然模式下，主播微笑就下雨；**开口时仍有笑意**并通过短暂多帧确认，就放烟花，不要求先做闭嘴微笑，也无需先送礼。直播画面之上有主播信息、观看人数、评论与礼物反馈；底部是礼物入口和可展开的礼物托盘。观众选择并送出礼物，会先看见明确的入场/送礼反馈；若礼物与主播随后或当前的表情匹配，预制的 AR 效果获得一次视觉升级。

**默认自然模式的基础体验：**没有送礼也能用真实表情触发“微笑下雨、大笑炸烟花”；烟花粒子要与随头移动的区域发生可见的物理碰撞。礼物可作为视觉加成；另将“送礼后才开放表情联动”列为可切换的场景假设，不替代默认体验。雨、烟花的造型与节奏先设计好，网页运行时只判断表情、选择预设、模拟粒子运动与碰撞，不即时生成新特效。

**当前交付：**可执行的需求／验收说明、可在本机浏览器中预览的直播间网页 Demo、200 字以内复盘 PDF，以及供用户上传 GitHub 的源码包和公开构建。照片／视频仅作为开发版标明的备用测试输入，并走同一识别链路。公开 HTTPS 链接、Public 代码仓库与真人／实体手机验收仍待上传部署及现场验证。

微笑雨的第二轮视觉设计、平台资料依据和验收边界单列在[雨效方向与验收](./part2-rain-direction.md)；本文保留完整 Part 2 范围。

**先解决最大风险：**直播间是否像真实观看体验而非开发测试台；何时开放玩法、由谁开启、观众能否看懂场景入口与表情触发的关系；真人已经笑起来时系统是否及时回应；只张嘴是否被错误判为大笑；粒子碰到头部外围时能否看清折返或擦边滑走。

## 1. 需求边界与待验证的假设

| 类别 | 内容 | 处理方式 |
|---|---|---|
| 原始需求明确 | 直播间里微笑下雨、大笑炸烟花；烟花粒子与用户头部发生可见碰撞；相机中的面部表情与动作驱动对应效果 | 先做出可复现的实时镜头与表情链路；需求没有指定玩法入口或礼物前置条件 |
| 用户本轮明确安排 | 复刻 TikTok LIVE 的观看界面，直播区用实时摄像头模拟主播；下方有可选/可送的礼物，礼物在主播画面上表现并与主播表情结合；先做本地网页 | 本版主界面与交互链路的依据 |
| 真实 TikTok 交互事实 | LIVE 画面底部有 Gift 入口；选择礼物、查看所需 Coins、点 Send；直播礼物会出现在画面上 | 只借鉴已经核对的结构与送礼顺序，见文末来源 |
| 入口场景假设 | 默认自然触发、礼物后短窗、PK 阶段、主播选定的话题片段都是可能的开放方式；稳定表情才决定雨或烟花 | 作为四个候选场景对照，不冒充 PM 已确认的规则 |
| 产品推断 | 用户要分清“场景已经开放”“礼物已送出”和“主播表情真正触发特效”；主播脸与互动效果均清楚，碰撞有惊喜但不刺眼 | 用原型和测试验证，不冒充平台已有机制 |
| 技术近似 | 以面部关键点估计二维或 2.5D 头部碰撞体，不重建真实头发和三维头模 | 明示模型边界，验收“轨迹真实改变” |
| 未给定 | 品牌资产、目标机型、真实直播流、PK 事件、主播话术语义、礼物目录及价格、支付/账户体系、商业指标目标值 | 礼物、Coins 与观众数为模拟值；PK 和话题片段由本地手动模拟，不声称平台接入或自动听懂主播讲话 |

面部算法在这里识别的是**动作代理信号**，不是人的真实情绪或是否发出笑声。页面文案只说“微笑”“大笑动作”，不宣称情绪诊断。

### 四种互动入口假设

原始需求只定义“表情对应什么效果”，没有规定玩法何时开放、由谁发起。为避免把一种场景猜测写成需求，原型把**场景开放**与**表情触发**分开：入口让玩法处于可触发状态，有效人脸与连续表情证据才启动雨或烟花；演出持续、互斥、收束与冷却仍共用同一套规则。

| 候选入口 | 开放时机 | 待验证的问题 |
|---|---|---|
| 自然触发（默认） | 直播中持续开放，主播微笑或大笑即可启动对应效果；礼物只做可选加成 | 反应是否自然，是否会因主播日常表情而过频出现 |
| 礼物后短窗 | 观众送出互动礼物后，在有限时间内等待对应表情；礼物发送立即有回执，表情满足时才播放联动特效 | 观众会否理解“已送出”和“待表情触发”的区别；短窗多长合适 |
| PK 阶段 | 主播或运营开启 PK 互动阶段后，再由主播表情触发雨或烟花 | 集体情境能否让特效更有参与感，是否干扰正常观看 |
| 主播话题片段 | 主播在讲趣事、回应弹幕等内容片段前手动开启互动，片段结束后关闭 | 内容情境是否让下雨与烟花更有梗、也更易传播 |

网页实验台可以手动切换这些假设；PK 与话题片段仅模拟“场景已开启”，**不接入真实 PK 事件、不调用麦克风，也不自动理解主播说的话**。自然触发是当前基础验收路径，其他入口属于产品实验，不能据此宣称已验证留存或付费价值。

## 2. 按结果拆解需求

采用“期望结果 → 用户机会 → 方案 → 高风险假设 → 验证”的产品发现路径；同时逐项检查用户价值、易用性、技术可行性和业务适配四类风险。这是拆解需求的工作方法，不等于已经做了用户访谈或验证。[1][2]

| 层次 | 本项目的定义 |
|---|---|
| 期望结果 | 一眼认出是直播间；能选礼物、送礼并看到即时回执；微笑/大笑能在摄像头画面上产生相应效果；礼物与表情的叠加可理解，烟花碰头可观察 |
| 主要用户 | 直播观众是界面的主视角；镜头前的主播是被互动者。为单机测试，同一人暂可兼任两个角色 |
| 机会 1 | 原“AR 工作台”使人先看到按钮和参数，而不是直播：需要视频满屏、控件浮于直播画面之上 |
| 机会 2 | 需求未限定触发场景：默认让表情自然触发，同时对照礼物后、PK 阶段与主播手动开启的话题片段；送礼当下始终有独立回执 |
| 机会 3 | 真人开口笑时嘴角分数会波动：应同时观察当前张嘴与当前笑意，辅以双颊信号和多帧证据；不把过去笑过后的一次 O 嘴误判为大笑 |
| 机会 4 | 粒子不可信或盖脸：需要少量醒目的火星在头部外围折返或擦边滑走，并保留碰撞前后的可追踪拖尾 |
| 候选方案 | 直播观看页＋底部礼物托盘；旁侧实验台切换入口场景；预设计雨/烟花与礼物入场动效；场景开放与表情事件分层；头部近似碰撞体；实时相机为默认输入 |
| 首轮关键假设 | 单机“本机镜头即主播”足够清楚；不同开放时机不会混淆送礼与特效的因果；脸部模型能区分轻笑、强笑和只张嘴；二维碰撞观感可信 |
| 本地验证 | 四种入口场景与表情组合对照；直播间识别与送礼流程盲测；正反例素材与真人摄像头；碰撞对照；性能与设备记录 |

没有真实使用数据时，不能把“增加直播留存/付费”写成已证明的目标。本地原型先用代理指标：首次识别为直播间的比例、送礼完成率、送出/待升级/升级三阶段的理解度、误触发率、碰撞可辨认度和画面流畅度。后续真实试用才能决定是否投入平台直播集成。

## 3. 用户任务与体验流程

**核心任务：**进入直播间后看到自己的实时镜头被当作主播画面；默认自然模式下，微笑引发雨，直接开口笑引发烟花；移动头部观察火星在头部外围偏折。观众还可以在底部选礼物、送出，看见礼物进入直播画面，并在对应表情出现时给效果一次可感知的升级。礼物后、PK 和主播话题片段另作为开放时机的实验。30 秒内理解这一因果是设计目标，须经真人试用核对。

1. **进入直播间：**直接呈现 9:16 的实时摄像头主播画面，打开页面就请求相机权限，仅取视频、不录音；授权失败或设备不可用时，在直播框旁的“互动实验台”显示明确状态、重试和摄像头开关，不自动播放预设人物或演示片段。视觉打磨期可从实验台手动切换图像模拟输入，所选素材仍替换同一个直播画面。
2. **观看：**顶部有主播头像/昵称、模拟观看人数、关注或关闭；中下部可见精简评论和系统消息；底部有评论输入样式、礼物与分享等入口。识别、输入来源和演出／冷却状态集中在直播框旁的实验台，不覆盖主播画面。
3. **选择与送出：**点底部 Gift 拉起深色半透明礼物托盘；可见多种礼物、图标/名称/模拟 Coins、选中态和明确的“送出”按钮。送出后托盘收起，立即出现礼物入场动效与“你送出 ××”的直播系统消息；Coins 仅用于模拟展示，不购买或扣真实余额。
4. **表情基础效果：**默认自然模式下，不送礼也可触发：短时稳定的嘴角上扬只启动一次聚云、闪电开场，此后维持雨幕直到表情不再满足微笑；若演出门控空闲，**当前开口且当前有笑意**并得到多帧确认，就启动持续分波发射的烟花，直接从平静表情开口笑也有效。张嘴时嘴角分数可能回落，可结合双颊变化辅助；仅靠过去笑过或现在只张嘴都不触发。雨或烟花持续期间继续跟踪头部供雨滴和火星碰撞。稳定回到平静后，当前效果平滑收束，收束完再等待 2 秒冷却；若从微笑直接变大笑或从大笑直接变微笑，旧效果先收束，新的当前表情再触发另一效果，互斥且不要求平静过渡。短暂表情波动不立刻关停，也不把旧识别事件排队补放。醒目的火星碰到头部外围后折返，只在实际撞击点带出短暂破裂光波与二次小火星，不沿整张脸形成光圈。
5. **礼物 × 表情升级：**互动礼物有“雨系”和“烟花系”。送出后先完成入场反馈，再在一个明确、有限的窗口内等待对应表情；当前已满足表情则即刻承接。匹配时播放预设计的增强版本，例如雨滴更有光泽/局部串成花纹、烟花出现第二层有序花瓣和更亮但受控的碰撞火星。未匹配时不强行播放该表情特效；超时给平静的结束反馈。默认自然模式中，礼物并不是基础雨/烟花的必要条件；礼物后短窗模式单独验证“礼物开启短时表情互动”是否更适合直播情境。
6. **离开与异常：**退出房间、主动关闭摄像头或页面切后台时释放媒体轨道；恢复或重新打开时重连；无脸时停止新表情事件，旧粒子自然消散；切后台后恢复不能出现重复循环。权限拒绝、设备占用、模型失败各有可行动的直播内提示。

### 直播页信息层级与视觉规则

- **第一层：**完整竖屏视频，占手机视窗主体；电脑端直播间与低干扰的实验台并排，窄屏时实验台排在直播间下方。摄像头人像不因礼物托盘或粒子被持续盖住眼口。
- **上缘浮层：**头像、昵称、轻量关注按钮、观看数和关闭等直播内容。采用半透明深色底和文字阴影，避免对明亮视频失去可读性；摄像头开关、输入来源、LIVE／本地演示与互动挑战说明不叠在主播画面上。
- **下缘浮层：**最近几条评论/送礼系统消息在视频左下方渐出；评论输入、礼物、分享等控件停在安全区；可以有少量右侧爱心反馈，但不喧宾夺主。
- **礼物托盘：**由底部滑入，约占手机可视高度的一半；深炭色半透明底、三列网格礼物卡、图标/名称/Coins、小型分类与模拟余额、明确的选中态/送出按钮。保留上方视频可见区域，让用户送礼时仍能看到主播。具体高度、分类、货币数字属于原型设计，不宣称与某地区当前 TikTok 像素一致。
- **动效叠层：**礼物入场为 0.5–1 秒的局部动画；雨/烟花发生在直播视频上，不挤占正文 UI。高级礼物的视觉份量可更强，但送礼反馈、表情升级和碰撞三个瞬间要有先后，不同时全屏爆亮。

### 礼物交互契约（本原型的候选规则）

下表描述默认自然模式：礼物即时送出，并对符合表情条件的效果加成。礼物后短窗模式复用相同的送出回执和表情判断，但把互动礼物作为短时开放入口；这是可切换的产品假设，不改写原始需求，也不替代默认模式的无礼物验收。

| 事件 | 画面与状态 | 边界 |
|---|---|---|
| 点 Gift → 选礼物 | 托盘弹出；选中卡有清楚高亮，Send 才可用 | 这一步不触发表情特效 |
| 点 Send | 立即收托盘、显示礼物入场和系统消息 | 保证每个礼物都能看见送出反馈，即使主播保持中性 |
| 送出雨系礼物 | 给下一次微笑效果加一次升级；若已在微笑，立即升级当前雨幕 | 只影响雨，不把中性脸强行判为笑 |
| 送出烟花系礼物 | 给下一次已确认的大笑爆发加一层预制形态与碰撞火星；若当前已满足大笑条件，立即升级当前爆发或播放这次礼物的专属爆发 | 表情自发的烟花仍遵守冷却；当前只张嘴、没有笑意时不兑现烟花 |
| 等待、超时或重复送礼 | 可见简短待触发提示；候选等待窗 8 秒；超时平静解除。首版仅保留最近一件待触发互动礼物；新的互动礼物替换旧等待，普通礼物不取消等待 | 此时礼物已“送出”，只是 AR 加成未兑现；文案不可混淆。8 秒待真人测试再定 |

最小礼物目录应有几种可选礼物，其中至少一件雨系、一件烟花系，并可加入普通礼物来验证“送礼入场但无表情加成”。名称、价格和视觉素材均为演示资产；不冒充 TikTok 真实礼物库存。**真实 TikTok 的送礼步骤与视觉结构是参考；“礼物在指定表情下升级”和单机摄像头扮演主播是本方案的自定义机制。**

### 状态与优先级

以下表情与演出状态以默认自然模式为基线。礼物短窗、PK 与话题片段模式只在前面增加“场景已开放”的条件；开放场景本身不等于识别到笑容，不能绕过同一表情证据与碰撞链路。PK 与话题片段先由实验台手动模拟，不读取平台事件或讲话内容。

| 状态 | 进入条件 | 画面反馈 | 退出/特殊处理 |
|---|---|---|---|
| 直播间预览/待授权 | 初始或首次进入 | 直播结构可见，页面自动请求实时摄像头；实验台显示镜头状态 | 授权成功即显示实时画面；失败可在实验台重试或检查摄像头开关 |
| 加载/标定 | 摄像头就绪，识别尚不可用 | 实验台显示模型准备状态 | 成功后进入中性；失败提供重试 |
| 无脸/低置信 | 连续若干帧无法稳定定位 | 实验台温和提示，停止新发射 | 移除旧碰撞体；恢复后重新确认稳定 |
| 中性 | 有脸且笑容不足 | 清爽的直播视频与礼物入口 | 达到微笑门槛并持续一小段时间 |
| 微笑下雨 | 综合嘴角信号短时稳定，排除极端单侧误判，且演出门控空闲 | 两朵完整小云汇成大云、闪电；保持微笑期间持续全屏雨与头顶飞溅 | 稳定回到平静则渐隐；直接大笑则先收束雨，再切换烟花 |
| 烟花蓄势/爆发 | 当前开口且当前有笑意，经短暂多帧证据确认，且演出门控空闲；无需先闭嘴微笑 | 小火箭按预制波次持续升空，彩色大花与头缘碰撞 | 稳定回到平静则停止新发射并收尾；直接微笑则先收束烟花，再切换雨 |
| 收束与冷却 | 当前有效表情稳定退去，或直接切换到另一种有效表情 | 先让现有雨／火星平滑退场；回到平静后再冷却 2 秒 | 冷却完成用新鲜帧确认当前表情；直接切换另一效果不要求平静过渡 |
| 礼物已送/待加成 | Send 后，互动礼物尚未与表情匹配 | 独立于表情状态的系统消息、入场与轻提示 | 匹配、超时或另一礼物替换后结束 |

**优先级：**演出门控空闲时，系统错误/无脸 > 大笑爆发 > 微笑雨 > 中性；持续期间雨和烟花互斥。回到平静时收束并冷却，直接转换表情时只做收束、不额外要求 2 秒平静冷却；新效果仍须当前有效帧确认。礼物是并行的“已送/待加成”状态，不覆盖表情判断；人脸丢失不保留悬空的“幽灵头”。

## 4. 表情识别契约：输入、规则、反例

### 输入与特征

- 唯一默认权限为视频；不调用麦克风。实时相机与上传测试视频都进入同一检测、平滑、状态机管线。上传图片可用于静态表情触发与定位检查，不能证明“持续动作”“移动碰撞”或实时延迟。
- 使用左右嘴角笑容系数、双颊苹果肌变化、双眼笑意、下颌张开系数、由内唇间距相对嘴宽估计的张嘴程度、手部遮挡证据、脸部关键点与跟踪状态。开口与笑意可以同时出现，不要求先识别一段闭嘴微笑；嘴张开不能单独触发。手遮嘴时，口部信号不可靠，必须另外确认双侧苹果肌上扬及双侧笑眼；可见嘴角的笑弧或更强的双侧笑眼提供补充证据。
- 后续个体标定方案：约 1 秒中性样本和约 1 秒自然笑样本，取稳健统计量作为个人范围；标定失败使用默认区间并标出“未标定”。当前 Demo 尚未实现此步骤；数值、采样时长都需用真实素材调整。
- 原始值先平滑，再做进入/退出分离；短时间低置信输入应冻结或衰减，不把上一次强笑状态无限延续。

### 当前原型判定，阈值待真人测试后调整

| 事件 | 判定原则 | 候选时间与复触发规则 |
|---|---|---|
| 微笑进入 | 嘴角综合呈上扬趋势，至少一侧明显、另一侧有合理响应，且脸稳定可见 | 短时稳定约 250–350 ms；云与闪电入场一次，雨持续到表情稳定变化 |
| 微笑退出 | 笑容低于较低退出阈值，使用滞回 | 短暂回落不中断；稳定平静约 500 ms 后雨渐隐，直接大笑则优先切换 |
| 大笑进入：无遮挡 | 当前帧既有开口证据，又有嘴角笑意和双眼笑意；嘴角分数偏低时可用双颊变化辅助，但仍需当前最小笑意证据，不沿用过去笑容 | 候选约 300 ms、最近 5 帧中至少 3 帧支持；触发一次入场，持续笑时循环预制烟花波次 |
| 大笑进入：捂嘴 | 手确实遮住嘴、双侧苹果肌上扬且双侧笑眼成立；另需可见嘴角笑弧或更强的双侧笑眼。普通捂嘴、闭眼／眨眼及单侧脸颊变化均不算；遮嘴时模型误报张嘴也不能绕过此条件 | 候选约 450 ms，并由至少 3 个独立新鲜手部帧支持；真人阈值仍待实测 |
| 效果切换／再次触发 | 平静回落后的效果已收束且 2 秒冷却完成；或已直接确认另一种有效表情并收束了旧效果 | 当前新鲜帧须重新满足多帧确认；持续同一表情只维持当前效果，不因旧时间轴到点重开，也不要求先做平静表情 |
| 人脸丢失/推理暂缓 | 无可靠脸部追踪或短暂等待下一帧 | 短帧间隔不清空已积累的动作证据；超过识别宽限时间停止新事件并使碰撞体失效，不让旧脸无限延续 |

这些毫秒数是原型起点，不是训练模型的可信概率，也不是已实测的最终规格。最终阈值需在同一目标设备、不同光照和不同人脸上测试后调整，目标是避免误触发，同时不让用户夸张地保持表情很久。

### 必测正例与负例

| 输入 | 预期 |
|---|---|
| 中性 → 自然、嘴角稳定上扬 | 进入雨；无烟花 |
| 空闲时从平静直接开口笑，未先闭嘴微笑 | 多帧确认后启动烟花，保持大笑期间持续发射，优先于雨 |
| 空闲时轻笑 → 开口笑，嘴角系数短暂下降但仍有当前笑意 | 多帧确认后由雨平滑切换为持续烟花 |
| 雨播放中改为大笑 | 新的大笑保持约 180 ms 后雨进入收束；收束完成且大笑仍被新帧确认，就开始烟花；两者不叠加，不要求平静过渡 |
| 持续微笑超过旧版 7 秒 | 雨仍持续；两朵云不重新聚拢，闪电开场不机械重播 |
| 持续大笑超过旧版 9 秒 | 烟花继续分波升空；不重新触发一次新的整场演出 |
| 稳定回到平静 | 当前效果收束后进入 2 秒冷却；冷却后新鲜表情可重新触发 |
| 烟花中直接改为自然微笑 | 烟花停止新发射并收束，当前微笑得到确认后下雨；无须先回到无表情 |
| 左右嘴角分数不对称，但整体仍像自然微笑 | 能进入微笑；不因较弱一侧低于旧版硬门槛而持续漏检 |
| 推理帧间隔略长但仍连续有效 | 不能每次都重置大笑蓄势；单个新帧也不能凭等待时间直接触发 |
| 强笑持续很久 | 一次入场后维持烟花波次；不会按固定时钟每隔数秒重新开场 |
| 回落 → 再强笑 | 平静回落使烟花收束，经过 2 秒冷却及新的多帧确认后可重新出现烟花 |
| 讲话、惊讶、打哈欠，仅嘴张开或 O 嘴且当前没有笑意 | 不触发烟花；说话同时伴随笑意等真人边界仍需现场验证 |
| 普通捂嘴、捂嘴眯眼但双侧苹果肌没有上扬 | 不触发烟花；遮嘴本身不能代替面颊笑容证据 |
| 捂嘴且双侧苹果肌上扬、双侧笑眼稳定，笑弧可见或笑眼更强 | 多个新鲜手部帧确认后可触发烟花；真人摄像头正例仍待验证 |
| 单侧撇嘴、侧脸、瞬时笑一下 | 不轻易触发大笑；低置信时停止新事件 |
| 镜头里无人、多人、脸部分遮挡、低光 | 不沿用旧人脸；提示恢复。首版仅追踪画面中最清晰的一张脸 |
| 头部左右移动但不笑 | 不产生表情特效；若已有烟花，既有粒子可与移动的头继续碰撞 |

## 5. 视觉方向与特效资产说明

### 总体审美

**创意方向：**让微笑像一句轻松的开场玩笑：两朵完整的蓝紫珠光小云聚到头顶，再变成一朵大云，珍珠色短闪后下起明显的雨，发顶有细小飞溅；大笑则切换为另一轮热烈庆祝，小火箭升空，饱和多色大花持续铺满直播画幅。两段效果独立播放，不把同一次笑容叠成雨加烟花。微笑下大雨虽然反直觉，但原始需求已明确；因此云和雨要像可分享的趣味滤镜，而非灰冷的灾害画面。直播页本体保持 TikTok LIVE 风格的**真实视频优先、炭黑半透明 UI、少量高对比强调色**；色彩属于 AR 效果层，不给摄像头画面铺大面积深色滤镜，也不持续盖住人脸。

画面层次：摄像头人像是第一主角；礼物入场短暂经过中景；雨在前景与侧边经过但避开眼口密集遮挡，少量水珠落到虚拟镜头玻璃后向下滑；烟花主要从头侧上方或肩外侧起爆，部分粒子进入可碰撞区；评论和互动按钮只占安全边缘。人脸五官在大多数特效帧清晰可见，观看者一眼能读到“谁在触发”。原型说明明确它不接入真实 TikTok 直播或支付，不把演示标签放到直播画面上。

### 预制效果与实时规则的分工

先制作**固定的艺术语言**：礼物图标与入场姿态、粒子形状、颜色渐变、发光材质、拖尾纹理、爆裂形态、节奏曲线与音效候选（首版可静音）。雨与烟花至少有基础和礼物加成两个可辨认的预设。运行时不生成新的视觉概念；网页只根据送礼与表情事件选择预设、控制发射时机/强度，并模拟粒子坐标、运动与碰撞。这符合“先做好 AR 特效，再由网页触发”的意图，同时保留真实物理互动所需的实时计算。

| 特效 | 可执行的表现规格 | 刻意避免 |
|---|---|---|
| 微笑雨 | 两朵完整的蓝紫小云先从左右进入，在画幅顶部重叠并渐变成一朵大云，云内珠光透亮并有克制的细电光，云底在发顶附近渐隐；前中后三层雨丝随后覆盖屏幕，眼口区域减弱。雨滴打到发顶的各个实际落点时，冒出短暂向上弹起的小水珠，外侧落点可带出短水痕，不沿头部描边。少量水珠撞上虚拟镜头玻璃，短促飞溅、汇流并沿弯曲水痕向下滑，五官附近逐颗淡化。云与闪电开场只播一次，雨幕随后随微笑持续；礼物版进一步增加珠光层与雨量 | 写实恐怖乌云、灰暗灾害感、明显的头部轮廓线、整屏水膜、连续挡住双眼、突然开关 |
| 烟花升空 | 白金色燃烧火核从画面下方和两侧分波升起，短喷焰、断续金橙火星及淡烟沿弧线留下可辨的轨迹；大笑保持时以有变化的预制波次继续升空 | 三角箭头、均匀光棒、只有突然出现的爆点、在脸中央蓄满亮点 |
| 连续绽放 | 牡丹、菊形、垂柳、棕榈枝和重瓣花型分波绽放，金、洋红、青、紫、绿、橙色大花覆盖上方、两侧和下半画面；快粒子形成外轮廓，慢粒子构成花芯，持续时间由大笑保持时长决定 | 只有一个静态 GIF、稀疏小爆点、持续全屏白闪 |
| 碰撞瞬间 | 背景大花中少量较亮的主火星沿可追踪拖尾朝头部飞来；触到随脸移动的近似边界后改变轨迹，脸侧内沿出现短促的彩色受光与亮芯，碎火星朝碰撞所在侧外抛成小花，破裂光波只出现在局部且频繁接触时限流。眼口附近的普通火星逐粒降低透明度，不使用整脸椭圆挖空或头缘描线 | 在五官上铺满光圈、单纯遮住粒子、形成整脸空气圈，或每个碰撞都炸成同等强的白斑 |
| 余辉 | 单朵烟花渐落并熄灭，新一波在大笑持续期间接续升空；表情稳定退出后停止新发射，既有火星短暂淡出，面部始终可辨 | 中段突然空场、烟花永久悬浮或突然清屏 |
| 礼物入场与加成 | 送出时先有清楚但短暂的礼物图标入场；表情匹配后，雨用局部珠光纹理/色彩层升级，烟花用预制的第二层轮廓和更清楚的碰撞火星升级 | 礼物送出后完全没有反馈；礼物与表情同时无序叠成整屏白光 |

高质量的验收不是“粒子越多越好”，而是**直播画面仍真实、送礼反馈清楚、表情升级有起承转合、碰撞可见、运行稳定**。建立对照用例：中性直播间、打开礼物托盘、送礼入场、基础微笑雨、礼物加成雨、基础烟花、礼物加成烟花、碰撞、余辉的关键帧＋完整流程录屏，逐项检查遮脸、颜色、节奏和拖尾。至少让一位没有读说明的人复述“礼物送出”和“表情触发/升级”各发生了什么；若无法复述，先改设计而非继续加粒子。

## 6. 头部碰撞的行为规格

**验收定义：**烟花粒子碰到头部后，其位置与速度遵循明确规则发生变化。把粒子放在人脸前层、在脸附近播放一段动画、让光晕跟着头走，都不足以证明碰撞。

第一版由面部关键点生成随头移动的**屏幕空间椭圆**，近似覆盖额头、两颊、下颌的可见头面区域；火星可在椭圆外缘接触，让折返更容易被看到。上边界根据脸部尺寸推断，**并未分割真实头发、耳朵或三维头模**，应作为已知近似。视频、关键点、粒子舞台使用统一的镜像、裁切和缩放映射；窗口尺寸改变后立即重算。

粒子带有位置、速度、半径和生命周期。每一步先推进位置，再检测是否穿入头部边界；若碰撞，纠正穿透，按接触法线与相对速度反射/滑移，再让少量能量衰减。移动头部的速度会有限地影响火星，但跟踪跳变不能把粒子“打飞”到屏幕外。首轮可用屏幕空间物理，不宣称三维刚体精度。高速粒子、低帧率、丢脸和轮廓突然跳跃需要额外处理，以免穿头、粘边或速度爆炸。

开发调试模式可显示半透明头部边界、碰撞点、接触法线和本次碰撞次数；正常体验中隐藏。需要做一组**同一初始粒子轨迹**的有碰撞/关闭碰撞对照，以及静止头/移动头对照：观众应能指认主火星碰到头部外围后的折返、擦边与之后的运动区别。调试开关只供验证，不代替真实画面效果。

推荐实施顺序是：①先锁定直播间的手机比例、信息叠层和礼物托盘；②确定礼物入场、基础雨/烟花及其加成版的关键帧与节奏；③用测试输入跑通送礼/表情双输入状态机；④接入相机、真实碰撞与隐藏调试可视化；⑤用样本和真人两条证据链调阈值、优化直播画面；⑥完成本地验收。若某视觉素材无法实时改变轨迹，则该素材不适合作为碰撞粒子主体。

## 8. 本地 Demo 验收协议

验收分成四层，不能拿其中一层冒充另一层：

1. **确定性逻辑测试：**用合成特征序列覆盖“轻笑、左右分数不对称、从平静直接开口笑、先笑后开口且当前仍有笑意、张嘴时笑容分数回落但双颊支持、过去笑过而现在仅张嘴、O 嘴、间隔略长的有效帧、单帧误触发、丢脸、持续微笑超过旧版 7 秒、持续大笑超过旧版 9 秒、稳定平静后收束与 2 秒冷却、雨后不回落直接开口笑、烟花后不回落直接微笑、冷却期不抢播、冷却后只凭新鲜帧触发”；礼物序列覆盖“未选直接 Send、普通礼物送出、雨系礼物后微笑、烟花系礼物后大笑、已在目标表情时送出、等待超时、新互动礼物替换旧等待、普通礼物不取消等待、默认自然模式无礼物效果”。另测四种场景入口：礼物短窗未开放时不播、送礼后与正确表情组合才播、PK/话题阶段仅在手动开启时有效、切回自然模式即可直接按表情触发。检查状态切换、入场回执、加成次数和冷却；用固定粒子初始条件验证碰撞前后速度与轨迹。此层证明代码规则。
2. **直播页操作与视觉测试：**在手机尺寸和桌面尺寸逐步走完“进入直播间→看见主播→打开 Gift→选择→Send→入场回执→表情升级→退出”；礼物托盘打开时仍能看到人脸，关闭后可继续互动；待触发与超时不被误解为发送失败。留可核查的关键帧/录屏。此层证明产品体验和界面。
3. **图片模拟验证：**当前可在直播框旁的“互动实验台 → 画面输入”中选择内置表情图、上传本地图片或播放连续表情视频；素材在主播画面位置经同一人脸模型、表情状态机与门控识别，再按实际结果自动触发 AR。平静、只张嘴和平静捂嘴应保持不触发，微笑应触发雨，无遮挡开口笑应触发烟花。捂嘴正例还需同时得到双侧苹果肌与笑眼证据；原 `covered-laugh.png` 图片在新规则下双颊分数为 0／0，不能当作正例。此层只能说明固定样本的识别链路和视觉表现，不能宣称真人摄像头准确率已通过。临时入口与素材副本在正式交付前移除；不同角度、遮挡和动态移动仍由真人相机测试覆盖。
4. **真人相机测试：**首次授权、拒绝、进入/离开直播间、真实轻笑与强笑、说话/打哈欠、头部移动、窗口缩放、切后台再返回；同一个人在摄像头前送雨系/烟花系礼物并做对应表情。记录设备与浏览器；确认实际授权、实时采集和匹配成功。若开发者不在场，这层应明确标为待现场复核，不编造通过结果。

| 验收维度 | 最低可观察标准 | 证据 |
|---|---|---|
| 直播间识别 | 初见者把首页认作正在观看的竖屏 LIVE；人物视频是主体，主播信息、评论和礼物入口在合理位置；样本/调试入口没有把它变成测试台 | 两种视口截图＋简短盲测记录 |
| 送礼流程 | 多个礼物可选择，选中态与 Send 明确；送出当下有可见的礼物入场和消息，托盘正常退出；模拟 Coins 无实际支付 | 操作录屏＋状态/系统消息记录 |
| 互动入口 × 表情 | 默认自然模式无礼物也触发基础雨/烟花；礼物短窗、PK 和话题片段只在场景开放后响应稳定表情；只张嘴不放烟花；切回自然模式后无需重新送礼 | 四种入口与表情组合对照＋负例记录 |
| 礼物 × 表情 | 自然模式下，雨系送出后微笑版升级、烟花系送出后强笑版升级；只张嘴不兑现烟花加成；超时不把送礼判失败 | 无礼物/有礼物同输入对照＋负例记录 |
| 正确触发 | 轻笑出现持续雨；直接开口笑启动持续烟花；只张嘴/O 嘴不爆；持续保持不定时重启，平静回落后平滑退场，直接切换另一表情时互斥且无须平静过渡 | 状态记录＋视频截图/录屏 |
| 物理碰撞 | 至少三次清楚的粒子接触，接触后轨迹与无碰撞对照不同；头部移动改变碰撞位置 | 调试画面＋同轨迹对照 |
| 视觉 | 直播 UI、礼物入场、基础与加成效果风格协调；五官保持可读，爆发和余辉节奏清楚；外部观看者能复述送礼与表情的因果 | 关键帧＋短录屏＋观察记录 |
| 稳定 | 权限失败可恢复；无脸不继续触发；保持强笑不刷爆；运行 3 分钟不出现持续粒子堆积或明显内存上升 | 操作记录＋粒子计数/帧耗时 |
| 性能 | 在至少一台写明的目标设备上测首次模型就绪时间、识别到特效的延迟、爆发期间帧耗时 P95；数值公开记录，未达标时说明 | 测量表；目标值需先与实测基线协商 |

不预先宣称“精准”达到某个模型精度百分比。可以在固定测试集上统计真阳性、假阳性与漏检，单列说话/打哈欠负例；素材数量不足时只报告逐例结果，不用小样本包装为总体准确率。

## 9. 风险与决策点

| 风险/未验证假设 | 早期证据 | 处理决策 |
|---|---|---|
| 首页仍像 AR 测试台而不像直播 | 初见者先注意到模型/样本/参数，未看到主播与礼物 | 视频满屏、直播浮层优先；图片验证单独成页，直播页没有测试入口 |
| 送礼后等待表情像“没送成功” | 用户重复点 Send 或问钱是否扣了 | Send 立即有礼物入场和系统消息；待加成、超时文案与“送出成功”分开 |
| 把礼物场景误当唯一入口 | 默认自然模式也只有送礼后才下雨/放烟花 | 无礼物自然触发列为 P0；礼物短窗只作为单独可切换的场景实验 |
| 复刻导致平台接入被误解 | 用户以为真的在 TikTok 开播、给真实账号打赏 | 在产品说明和验证页明确模拟观众/Coins、无支付与账号功能；真实 UI 参考与原型规则分开说明 |
| 表情强度因人、光照、镜头变化很大 | 同一规则在不同素材上不一致 | 综合左右嘴角并限制极端单侧误判，结合张嘴几何与多帧时间证据；后续视真人测试再考虑个体标定 |
| 只张嘴触发烟花 | 说话/打哈欠负例失败 | 同时要求当前开口和当前笑意，辅以多帧确认；过去笑过、此刻仅张嘴与单个偶发帧均不触发 |
| 粒子“穿过”头或跟错位置 | 调试轮廓与视频偏移、低帧率时穿透 | 单一坐标映射、限步/扫掠检查、丢脸清除碰撞体 |
| 画质高但遮住脸 | 五张关键帧中眼口被频繁覆盖 | 改起爆位置、限制中心亮度与重叠粒子，降低次要拖尾 |
| 过度平滑造成反应慢 | 用户已笑但雨/烟花延迟明显 | 降低平滑窗口并保留防抖；分别记录触发延迟和误报 |
| 模型和渲染争抢主线程 | 烟花爆发时卡顿或输入滞后 | 控制推理频率、只保留最新帧、粒子硬上限；必要时验证 Worker 可用性 |
| 用户无法理解“微笑下雨” | 盲看者复述错误 | 先强化云汇聚、云内亮起、落头小水珠的视觉因果，再用无说明盲看验证；不在直播画面加玩法文案，也不擅自改原始需求中的表情映射 |
| 测试素材表现好、真人失效 | 虚拟输入通过而摄像头失败 | 两条证据链独立报告；最终必须真人摄像头复核 |

本说明中的候选阈值、颜色、节奏和礼物等待窗可在实测后调整；需要保留修改原因和前后证据。TikTok 界面随地区、版本与直播类型变化；本文只把可核对的共同结构作为参照，不声称某一截图就是 2026 年所有用户的当前布局。若未来要接入真实平台推流、账号或支付，它们是单独的产品/技术决策，不属于本轮本地原型。
